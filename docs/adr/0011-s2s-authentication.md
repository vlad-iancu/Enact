# ADR-0011: Service-to-service authentication with per-service Ed25519 JWTs and YAML-distributed JWKS/ACLs

**Date**: 2026-08-04
**Status**: accepted
**Deciders**: Iancu Vlad-Alexandru (with Claude Code)

## Context

Since ADR-0004/0009 the services call each other over HTTP, but nothing
authenticated those calls: any process that could reach a port could invoke
any route, including internal ones such as kb-api's full-document-content
endpoint. User identity remains stubbed (`X-User-Id`, out of scope); what was
missing is *service* identity — which service is calling, and is it allowed
to.

## Decision

Every service holds an Ed25519 keypair. Outbound calls carry a short-lived
JWT signed with the caller's private key (`iss` = caller, `aud` = callee,
`exp` = now+60s, random `jti`, header `kid` = caller's key id) as
`Authorization: Bearer`. The callee verifies the signature against a JWKS of
all services' public keys, requires `aud` = itself, `exp` within a 5s leeway,
and `kid` = `iss` (no cross-service impersonation), then authorizes the
verified caller against its own per-route ACL — default deny. Untokened
requests get the identity `anonymous`, which only passes routes explicitly
allowing it; `"*"` admits any *authenticated* service, never anonymous.

Distribution: the JWKS and per-service ACLs are YAML files in the `s2s/`
directory (`s2s/jwks.yaml`, `s2s/acl/<service>.yaml`; private keys in
`s2s/keys/`, gitignored, generated by `make s2s-keygen`). Services receive
the *content* of these files (not paths) through environment variables
(`S2S_JWKS`, `S2S_ACL`, `S2S_PRIVATE_KEY`, `S2S_KEY_ID`), injected by
`scripts/start-services.sh`.

Wiring lives in `internal/s2s`: an `s2s.Config` embedded in every service's
config, `s2s.Load` at startup (fail-closed: missing or mismatched material is
a startup error), `Runtime.Filter` registered per business WebService
(deliberately NOT in the generic service runtime; health/home/swagger stay
open), and `Runtime.Transport` composed under the tracing transport in the
domain clients. Policy outcome: kb-api is fully internal (services only);
agent-api, inference, and model-management remain anonymous-accessible entry
points.

## Alternatives Considered

### Alternative 1: Shared static bearer secret (one token for all services)
- **Pros**: trivial to implement and distribute
- **Cons**: no caller identity, so no per-caller ACLs; any leak compromises the whole mesh; rotation is all-at-once
- **Why not**: caller identity is the point — the ACL needs to know *who* is calling

### Alternative 2: mTLS between services
- **Pros**: transport-level, industry standard, encrypts in transit
- **Cons**: certificate issuance/rotation infrastructure, painful local dev (five certs + a CA), authorization still needs an app-level ACL on top
- **Why not**: far more operational machinery for the same authz outcome at local-dev scale; JWTs keep the trust material to two YAML files and a keygen script

### Alternative 3: HTTP JWKS endpoint per service instead of distributed YAML
- **Pros**: standard OIDC-style discovery, rotation without restarts
- **Cons**: bootstrap circularity (fetching keys requires trusting the peer first), network dependency at startup
- **Why not**: static distribution is simpler and sufficient; the YAML file can later be served over HTTP without changing token semantics

### Alternative 4: RSA (RS256) instead of Ed25519 (EdDSA)
- **Pros**: broadest ecosystem compatibility
- **Cons**: much larger keys/signatures, slower signing, more foot-guns
- **Why not**: all parties are our own Go services; Ed25519 is smaller, faster, and misuse-resistant

## Consequences

### Positive
- Every cross-service request is authenticated and authorized; the verified caller is logged (`caller=...`) alongside the trace id
- Default deny: a new route is unreachable until its ACL rule is written — access is an explicit, reviewable YAML change
- Per-service keys mean per-service rotation (delete key file, re-run keygen, restart)

### Negative
- kb-api is no longer directly reachable from Bruno/curl without a token — internal by design
- ACL route keys must match go-restful route templates; a typo yields 403s (surfaced clearly in logs/response bodies)
- Token verification relies on loosely synchronized clocks (5s leeway, 60s TTL)

### Risks
- Private key leak allows impersonating that service until rotated — keys are gitignored, 0600, and local-only for now
- ACL drift as routes evolve — mitigated by default deny (drift fails closed, never open)
